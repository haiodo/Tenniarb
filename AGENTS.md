# AGENTS.md

## О проекте

Tenniarb - редактор диаграмм и экранов в формате `.tenn`: структура плюс вычисления, всё текстом.
Живая версия - Go (`go/`, окна на `gowt`). Swift-версия (`Tenniarb/`, `TenniarbTests/`,
`Tenniarb.xcodeproj`) остаётся в дереве как история: CI её не собирает, новые фичи идут в Go.

- Язык/платформа: Go, модуль `github.com/haiodo/tenniarb/go`; UI - `gowt` (AppKit под капотом)
- Вычисления: `goja`; рендер - `go/scene` (один движок: `go/render` удалён, классическая диаграмма — его профиль рисования в сцене)
- Формат: `go/tenn` (lexer, parser, printer), спецификация - `docs/spec/tenn-scene.md`

## Структура репозитория

- `Tenniarb/` - основной код приложения
- `Tenniarb/model/` - модель, операции, undo/redo, вычисления
- `Tenniarb/document/` - NSDocument-слой, парсинг/чтение/запись `.tenn`
- `Tenniarb/document/tenn/` - lexer/parser Tenn (`TennLexer`, `TennParser`)
- `Tenniarb/views/` + `ViewController.swift` + `SceneDrawView.swift` - UI и взаимодействие
- `Tenniarb/ElementScene.swift` - рендер диаграмм/текста
- `go/` - живое приложение. `go/tenn` - lexer, parser, printer; golden-тест на общих `web/fixtures`.
- `go/app` - окна, контур, сцены, правки агента в живом документе
- `go/mcpserver` - MCP-инструменты и сервис, который их держит
- `go/cmd/tenniarb` - приложение и CLI (`check`, `suggest`, `bundle`, `gen`, `install`);
  `go/cmd/tenniarb-mcp` - прокси MCP, `go/cmd/tenniarb-service` - сервис
- `go/skill/files/` - скилл агента, встраивается в бинарь
- `docs/mcp-bench.md` - задачи и методика замера прогонов агента
- `web/` - TypeScript-версия (план в `../my-tasks/tenniarb/plan.md`, раздел 3). npm workspaces `packages/*`,
  тесты `node:test` на `.ts` без компиляции. `web/bench/` - бенчмарки рендера, вне workspaces.
  **Паритет с Go обязателен**: web открывает и рисует те же `.tenn`, включая сцены (`auto-layout`, `use`,
  слоты, параметры, стили, картинки); файл, сделанный в Go, вставляют в web и смотрят целиком. Расхождение
  картинки - дефект. План - `../my-tasks/tenniarb/engine-unify.md`, раздел 4a.
  Стенд паритета: `go/cmd/tennlayout` печатает дерево Go, голдены - `web/fixtures/scene/*.layout.json`,
  сверяет `web/packages/render/test/scene-parity.test.ts`; `TestGoldensAreCurrent` в
  `go/cmd/tennlayout` падает, если голден отстал от фикстуры. Меняешь сцену - пересобери голден и
  прогони оба теста. Пиксельный тест сцены просит шрифт по имени (`font-family Inter`): стека
  Helvetica на Linux-раннере нет, иначе на картинке нет глифов.
  `web/packages/mindmap` - встраиваемый mind map без вычислений (план, раздел 6): текстовый протокол блока, бандл `dist/mindmap.js`.
- `TenniarbTests/` - unit tests (518 тестов, ~70% покрытия); `PerformanceTests` вынесены
  в схему `Tenniarb-Performance`. Схема скипает все остальные suite поимённо - при
  добавлении нового тестового класса список надо дополнить, иначе он попадёт в perf-прогон.
- `TenniarbUITests/` - UI tests (таргет собирается, но в схеме `Tenniarb` отключен: `skipped = "YES"`)
- `.github/workflows/` - CI и release pipeline

## Локальная сборка и тесты

Все команды собраны в `Makefile`, `make help` показывает список:

```bash
make install        # Go-приложение в /Applications, CLI и MCP в GOBIN, скилл, конфиг opencode,
                    # последним шагом kill-running: приложение, прокси и сервис
make app            # только .app (build/go/app)
make go-mcp         # build/go/bin: tenniarb-mcp и tenniarb-service
make go-mcp-install # оба бинаря в GOBIN
make go-cli-install # tenniarb CLI в GOBIN
make agent-install  # скилл и MCP во все три агента (opencode, codex, Claude Code)
make opencode-mcp   # то же в один агент: --opencode | --codex | --claude
make skill-install  # только скилл, без MCP
make kill-running   # остановить приложение, прокси и сервис
make build          # Xcode-сборка Swift-версии (история, не живая версия)
make test           # Swift-тесты (история)
make test-only T=TenniarbTests/LexerTests
make perf           # только performance-тесты (схема Tenniarb-Performance)
make lint           # SwiftLint
make lint-fix       # автокоррекции SwiftLint
make format         # swift-format --in-place
make format-check   # падает если код не отформатирован
make ci             # SwiftLint + Xcode-сборка и тесты (локально, для Swift-истории)
make clean
make web            # сборка web/packages
make web-test       # typecheck + тесты web/
make go-test        # go vet + go test для go/
```

Инструменты:
- **Линтер** - SwiftLint (`.swiftlint.yml`), ставится через `brew install swiftlint`.
- **Форматтер** - `swift-format` из Xcode toolchain (`.swift-format`), ставить нечего.

Performance-тесты исключены из основного прогона (36 сек из 36.5) через `SkippedTests` в схеме
`Tenniarb`. `-only-testing` не перекрывает `SkippedTests`, поэтому для них заведена отдельная
схема `Tenniarb-Performance`, а не флаг.

Если `xcodebuild` падает из-за plugin/runtime окружения Xcode, сначала привести локальный Xcode в рабочее состояние (`xcodebuild -runFirstLaunch`) и повторить.

## Приложение, сервис и MCP

- `tenniarb-mcp` - тонкий прокси; инструменты живут в `tenniarb-service`, один на пользователя.
  После правок Go-кода нужен `make install` (или `go install ./cmd/tenniarb-mcp ./cmd/tenniarb-service`)
  и переподключение MCP: opencode не поднимает умерший сервер сам.
- Скилл (`go/skill/files/*.md`) встроен в бинарь: `read_skill` отдаёт копию из сервиса, а
  `tenniarb install` кладёт те же файлы в `~/.config/opencode/skill/tenniarb-design` и
  `~/.agents/skills`. После правки скилла нужен и реинсталл, и пересборка сервиса, иначе агент
  получит старый текст.
- Каждый вызов инструмента пишется строкой в лог (`MCP_LOG` из `Makefile`, по умолчанию
  `~/Library/Logs/Tenniarb/mcp-calls.log`; `TENNIARB_MCP_LOG` задаёт путь, `off` выключает; 8 МБ, потом
  в `.1`): время, pid, клиент (`opencode`, `codex`), корень воркспейса, инструмент, `ok`, размеры входа и
  выхода, миллисекунды и начало аргументов (2 КБ). `make install` прописывает путь в конфигах агентов,
  поэтому лог есть без ручной настройки.
- `TENNIARB_PPROF` (`MCP_PPROF`, по умолчанию `127.0.0.1:6061`) поднимает `/debug/pprof/` в сервисе и в
  приложении: `go tool pprof http://127.0.0.1:6061/debug/pprof/heap`. Живёт в процессе, который уже
  запущен, поэтому включается только при следующем старте сервиса. Методика и задачи - `docs/mcp-bench.md`.
- Одна загрузка воркспейса (1.7 МБ `.tenn`, 29 файлов): 25 МБ живой кучи и 300 тысяч объектов, 260 мс и
  217 МБ аллокаций. Узел на каждую команду плюс разобранные `tenn`-узлы каждого свойства (`scene.Prop.Args`).
  Приложение держит одно дерево на открытый сценовый документ плюс `pending` во время правки: живая куча 2
  документов 85 МБ, пяти окон 97 МБ, остальное в RSS - тулкит (CoreAnimation, IOSurface, malloc). **Читать
  `inuse_space` pprof можно только сразу после GC:** без него в «живое» попадает мусор, и цифры вида 470 МБ
  на 2 документа означают не деревья, а `alloc_space`. Сервис кэширует деревья бюджетом в байтах
  (`TENNIARB_TREE_CACHE_MB`, по умолчанию 192 МБ, `mcpserver/host.go`), а не числом штук.
- Проверка правки инструмента - тест в `go/mcpserver`; живой сервис требует `go install` и `/mcps reload`
  и для проверки не годится.
- `make install` убивает приложение по SIGTERM: несохранённые документы уходят в
  `~/Library/Application Support/Tenniarb/recovery/<дата-время>/` и предлагаются при следующем старте.
  Сохранять окна перед установкой всё равно дешевле, чем разбирать восстановление.

## Правки `.tenn` агентом

- Только через MCP `edit` / `design`, не через Write/Edit и не через shell: файл, открытый в
  приложении, получает правку как undo-шаг, а автосохранение пишет её на диск не позже
  `AgentAutosaveEvery` (10 с) после последней правки агента; до этого строка помечена `*`.
- Правка библиотеки, которую монтирует открытая доска, сначала открывает окно этой библиотеки: у
  драфта есть undo и хозяин, а все доски показывают один и тот же текст.
- Новый файл доски: минимальное `element X { }`, затем строка `--from-file` в мастере, затем тело с
  `entry`. И `entry`, и имена `Libraries.*` резолвятся только через смонтированный мастер.
- Читать `.tenn` по пути как `layout`: `scene.LoadAuto`/`DiagnoseAuto` (контекст entry), не `LoadSource` -
  иначе библиотека не видит имён мастера.
- Компонент библиотеки часто `item`, а не элемент: строить элемент и брать его кусок по `Placed.Gfx`;
  `BuildElement` на `item` отвечает `a item is not an element`.
- После `edit`/`refactor` читать состояние второй раз: `read`, `get_state` и `layout` иногда отдают
  прошлый снимок (лаг в один вызов), и следующая правка по устаревшему тексту откатывает предыдущую.
  Пачка `refactor` в одном вызове тоже теряет часть правок: по одной операции с проверкой.
- `--from-file` внутри смонтированного файла считается от папки этого файла, а не от корня воркспейса:
  поиск монтирования ведёт текущий каталог по цепочке.
- `kind Component` формат знает, но никто его не читает: маркер без потребителя ничего не значит. Ставить
  `kind` и подключать того, кто его читает, одной правкой; `§` в имени компонента - наследие до `kind`.
- Плита `§ X` - подпись группы. Содержимое либо вкладывается в неё (тогда это обычный родитель, и проверка
  «ребёнок вылез за родителя» работает), либо лежит рядом; `§` в имени не нужен, а совпадение имени плиты
  с компонентом делает путь неоднозначным.
- `design` и `refactor` отказывают узлу из чужого файла: передавать файл, который его пишет, даже если
  путь начинается с мастера.

## GUI-тесты и QA

- В приложении должен быть `qa.Handle("reset", ...)`: `qatest.App(t)` зовёт его перед каждым тестом.
  Reset закрывает лишние окна и открывает стартовый документ, иначе окна и правки переезжают из теста в
  тест (gowt пишет об этом в лог, `docs/qa.md`, «State and isolation»).
- Размеры и наличие контрола брать из `a.Dump()`, а не с скриншота.
- Сообщение упавшего теста - `go test -json` с фильтром по имени; старые падения отделять от новых
  `git stash` одного файла, а не повторным прогоном всего набора.
- Функция, которая в UI ничего не нарисовала, возвращает и показывает ошибку: `if err == nil` вокруг
  картинки оставляет пустую панель без причины.
- Перед работой с gowt читать нужные разделы `gowt@<версия>/gowt.go` (`Canvas`, `ImageFrom`, `ListView`),
  а не искать по одному методу.
- QA-приложение стартует на `Example.tenn` - это классическая диаграмма, у неё пустая панель Items. Тест
  контекстного меню Items сначала открывает свой сценный документ и активирует его, иначе правый клик
  уходит в чужое окно.
- Визуальное (меню, подсветка, наведение, переносы в панели) из кода не выводится: либо оконный тест, либо
  владелец. В отчёте писать «не проверено», а не «должно работать».
- `make install` убивает приложение: незасохранённые драфты дизайна уходят в recovery. Перед сборкой
  просить сохранить окна, иначе правки, сделанные через MCP, теряются.

## gowt

- Из сессии tenniarb gowt не правится вовсе: ни код, ни тесты. Задание - файл `tenniarb/.work/gowt-task-<тема>.md`:
  что происходит (с видео и кадрами), где смотреть (`file:line`), что просим, приёмка, обход. Владелец
  передаёт его агенту gowt; здесь после релиза только бамп версии и правка под новый API.
- Черновики, оставленные в дереве gowt прерванной сессией, перечисляются в задании с решением «брать /
  удалить»: владелец решает, агент tenniarb их не откатывает.

## Правила внесения изменений

0. Пушит только владелец. Агент готовит правку и коммит, `git push` и релизы - на человеке.
1. Сохранять совместимость формата `.tenn`.
- Любые изменения в parser/lexer/persistence должны не ломать чтение существующих файлов.

2. Не обходить `ElementModelStore` при изменениях модели из UI.
- Операции должны идти через store, чтобы сохранялись undo/redo, уведомления и пересчет.

3. Учитывать потокобезопасность вычислительного движка.
- `ExecutionContext` синхронизирован через `syncQueue`; не добавлять доступ к JS-контексту в обход этой модели.

4. Сохранять текущий стиль построения UI.
- Окна/контроллеры создаются программно (`Document`, `Application`, `AppDelegate`), не добавлять storyboard/xib без явной необходимости.

5. Не вносить случайные изменения в `project.pbxproj`.
- Менять version/build settings только когда это часть задачи.

## Минимальная валидация перед сдачей

0. GUI-тесты открывают окна на машине владельца и забирают фокус: спрашивать разрешение перед
   `GOWT_GUI_TEST=1 go test ./app ...`. Обычные `go test ./...` окна не открывают.

1. Для любых Swift-изменений:
- `swiftlint lint --config .swiftlint.yml`

2. Для parser/lexer/persistence:
- `TenniarbTests/TennTests.swift`
- `TenniarbTests/PersistenceTests.swift`

3. Для Markdown/рендера текста:
- `TenniarbTests/MarkDownTests.swift`
- релевантные участки в `ElementScene.swift`

4. Для рендера/экспорта:
- `TenniarbTests/svh-generate/TestSVGGenerate.swift` (если затронут экспорт/scene rendering)

5. Для изменений в логике модели:
- релевантные тесты + проверка, что undo/redo и refresh-события не регресснули.

## CI и релизы

- CI workflow (`.github/workflows/ci.yml`) проверяет Go (vet + тесты на macOS, Linux и Windows), web-пакеты (typecheck + тесты) и гоняет GUI-тесты под Xvfb. Swift-приложение больше не собирается в CI: Xcode-проект остаётся в дереве как история.
- Release workflow (`.github/workflows/release.yml`) запускается по тегу:
  - собирает Release
  - архивирует `Tenniarb.app` в zip
  - публикует GitHub Release
  - обновляет `MARKETING_VERSION` в `Tenniarb.xcodeproj/project.pbxproj` на default branch

Перед изменениями release-логики проверять, что шаг обновления версии в `project.pbxproj` останется консистентным.
