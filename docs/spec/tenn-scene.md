# Формат `.tenn` с графом сцены (черновик)

Статус: черновик спецификации, этап 0.2. Источник решений: `my-tasks/tenniarb/roadmap.md`.

Пометки:
- **[решено]** - решение из roadmap (дата там же).
- **[предложение]** - вариант автора черновика, не принят.
- **[факт]** - проверено по коду или запуском.

Имена свойств в разделе 5 целиком **[предложение]**: roadmap фиксирует только `auto-layout` и `gap` в примере.

## 1. Грамматика

Грамматика не меняется **[факт]** (`lexer.ts`, `parser.ts`): команда = символ, затем аргументы (symbol, string, число,
`${...}`, `%{...}`, блок `{...}`), команды разделяются переводом строки или `;`. Новые конструкции - обычные команды
с новым смыслом. Путь `my.lib.button` - один symbol-токен (`detectSymbolType`: точки внутри символа допустимы;
сегмент, целиком состоящий из цифр, превращает токен в `floatLit`, см. вопрос 9).

## 2. Два уровня

1. `element` - дерево вложенности **[решено]**: разделы, ветви подходов, категории библиотеки, точки монтирования файла (`--from-file`),
   области видимости. Один element - одна сцена на холсте.
2. Содержимое element - узлы сцены **[решено]**: `item` (может иметь детей и auto-layout), `link`, `use`.

```tenn
element "Product" {                 // уровень 1: дерево
    element "Login" {
        item "Idea" { pos 0 0 }     // уровень 2: содержимое element "Login"
        item "Screen" {
            auto-layout column
            item "Title" { title "Sign in" }
        }
        link "Idea" "Screen"
    }
}
```

Что есть что:

| Конструкция | Уровень | Состояние |
|---|---|---|
| `element`, `item`, `link`, `pos`, `styles`, `display`, `layout`, `width`, `height`, `use-style`, `layer`, `corner-radius` | 1 и 2 | есть, `layout` - раскладка диаграммы element, не auto-layout |
| `element ... --from-file`, `use`, `slot`, дети у `item` | - | новые |
| Свойства auto-layout (раздел 5) | 2 | новые |

Узлы содержимого, которые не `item`/`link`, в brain map игнорируются при рисовании, но сохраняются (раздел 9).

## 3. Монтирование файла: `element ... --from-file`

**[решено 2026-10-27]** Файл подключается строкой `element "<имя>" --from-file "<файл>"` (3a). Старого `import`
в формате нет: выпущенных файлов с ним не было, строка `import` читается как обычное свойство.

```tenn
element "my_lib" --from-file "libs/my-lib.tenn"      // в корне файла или внутри element
element "Login" {
    element "demo" --from-file "../data/demo.tenn"
}
```

- **[решено]** Монтирование - это подключение поддерева другого файла в этом месте, а не экземпляр: без переопределений.
- **[решено]** Всё, что смонтировано в файле, видно его потомкам по общим правилам областей видимости, а смонтированному
  файлу - всё, что видно в месте монтирования (5a.1, 5a.19).
- **[решено]** Пути относительно файла со строкой, только внутри корня workspace (те же корни, что у MCP).
  Выход за корень - ошибка `validate`.
- **[решено]** Один файл в двух местах - то же поддерево, не копия; имена в нём разрешаются по каждому месту отдельно (5a.1).
- **[решено]** Правка внутри смонтированного поддерева пишется в исходный файл; редактор помечает такое поддерево,
  `validate`/MCP показывают, кого правка задевает.
- **[решено]** Цикл монтирования - ошибка с позициями всех `--from-file` по кругу.
- **[решено]** Printer пишет строку `--from-file`, не содержимое.
- **[решено]** Префикс пути - имя element; точек в имени нет. Область видимости монтирования = element, в котором стоит
  строка (или весь файл, если в корне), и все его потомки. Подмена: на другой ветви то же короткое имя резолвится в
  другую библиотеку.
- **[решено]** Короткий путь разрешается ближайшим определением вверх по дереву; полный путь снимает неоднозначность.
  Два element с одним именем на одном уровне дают неоднозначный путь - ошибка `validate`.
- Реализация: раздел 5a (области видимости, корень файла, сообщения о циклах).

## 3a. `element ... --from-file` **[решено 2026-10-27]**

```tenn
element "ui_kit" --from-file "ui-kit.lib.tenn"
```

- Всё содержимое element берётся из корня указанного файла вместо блока `{ ... }`: его `element` становятся
  дочерними, `item`/`link`/`use` и свойства корня - содержимым. Имя element - из строки, не из файла. Блок вместе
  с `--from-file` - ошибка. Ничего отдельного не нужно: `use ui_kit.Button as b` идёт по обычным путям element,
  дерево element в приложении показывает его как любой другой.
- Путь относительно файла со строкой, только внутри корня workspace; выход за корень, цикл (ошибка с позициями
  всех `--from-file` по кругу) и нечитаемый файл - диагностики с позицией строки. Element с плохим файлом
  остаётся пустым, строка сохраняется.
- Один файл в двух местах - то же поддерево, не копия (go/scene делит списки узлов, разрешение имён идёт по каждому месту, 5a.1;
  go/model читает копию на каждый element, потому что у элемента модели один родитель).
- Имя внутри смонтированного файла ищется в файле, затем в месте монтирования и выше до входного документа (5a.1), поэтому библиотеку монтирует один раз входной документ.
- Printer и persistence пишут только строку `--from-file`, содержимое не печатается: сохранение документа
  не вкладывает библиотеку в файл.
- **[решено 2026-10-27]** Смонтированный element - обычная строка левого дерева, отдельной секции библиотек нет;
  строка с `--from-file` помечена значком-ссылкой. Список Insert Component строится по тем же смонтированным файлам.
- **[решено 2026-10-27]** Правка внутри смонтированного поддерева пишется в исходный файл, основной файл не
  меняется. Классическая правка (`ElementModelStore`, undo и redo тоже) пересобирает текст файла сплайсером, как для
  документа; правка scene-узла пишется в файл узла (`Pos.File`), тем же ограничением "не добавлять ошибок scene". Окно
  держит текст файла до сохранения: строка element в дереве показывает `*`, пока в файле есть несохранённые правки;
  запись идёт тем же отложенным и атомарным автосохранением, что и у документа (также при Save и закрытии окна), после
  записи `*` пропадает. Если файл открыт в другом окне, правка становится правкой того окна (его undo, его `*`, его
  сохранение). Файл, изменённый другой программой после первой правки, не перезаписывается. MCP `edit` с путём этого
  файла по-прежнему пишет его напрямую. **Потолок:** перенос element из документа в смонтированный файл и обратно
  (`ErrMounted`); правка в смонтированном файле, меняющая набор element, пересоздаёт их, ссылки редактора на старые
  (выбранный element, шаги undo до правки) устаревают.
- Модель: `Element.FromFile`; `model.MountFiles` заполняет содержимое по scene-дереву (оно разбирает пути и циклы),
  `KindOfModel` считает такой element признаком сцены, когда ничего другого нет.

## 4. `use`

```tenn
use my.lib.components.button as ok {        // полный путь
    title "OK"
    color red
}
use button as cancel { title "Cancel" }      // короткий путь, ближайшее определение вверх
use Screens.Window.Footer as footer          // узел содержимого внутри element Screens
```

Синтаксис: `use <path> as <name> [{ overrides }]`. `as` обязателен **[предложение]** (имя экземпляра нужно для путей,
`${...}` и переопределений в экземпляре экземпляра).

### 4.1 Что можно взять **[решено]**

Любой узел на любом уровне: item brain map, item окна, кнопка внутри него. Экземпляр `element` целиком **[предложение]**: roadmap
говорит про "любой узел на любом уровне", путь идёт через element-ы. Отдельного `component` нет. Экземпляр можно создать рядом с определением.

**[решено 2026-10-28, реализовано в go/scene]** Положение экземпляра - его собственный `pos` (в блоке `use` или в `at`
вложенного `use`); без него экземпляр стоит в 0 0 в abs-родителе или там, куда его ставит раскладка родителя. `pos` корня
определения не наследуется: он описывает только место компонента на холсте библиотеки. Остальные свойства корня (размер,
цвет, раскладка) экземпляр наследует по-прежнему. Это относится и к экземпляру экземпляра: `pos` блока `use` определения
тоже место определения. `penimport` поэтому не пишет `pos 0 0` у экземпляров.

### 4.2 Путь **[решено]**

- Сегменты через `.`: сначала имена `element`, затем имена узлов содержимого (`my.lib.screens.Window.button`).
- Обычный сегмент - это ключ имени: сегмент нормализуется как в вычислениях, `convertNameJS` ([факт] `execution.ts`):
  символ, не буква/цифра/маркер Unicode (`\p{L}\p{M}\p{N}`), заменяется на `_`. `"Primary button"` -> `Primary_button`;
  регистр сохраняется. Старые пути с `_` работают по-прежнему.
- **Сегмент в двойных кавычках** сравнивается с `Node.Name` как есть (NFC, без нормализации), поэтому имя с пробелами,
  запятыми, скобками, дефисами или точкой адресуется без угадывания ключа:
  ```tenn
  use Kit."My Button" as b
  at "2 Пространства - пусто" { title "…" }
  replace "Кнопка (primary)" { … }
  use "Product"."My Button" as p
  ```
  Кавычка внутри имени пишется `\"` (лексер уже так читает строку: `cc == '\\' && next == '"'`). Обратный слэш -
  обычный символ строки, не экранирование. Кавычить имеет смысл и элемент, и item, и имя slot в `at`; путь
  `A."B.C".D` - сегмент `B.C`, а не два сегмента `B`, `C`.
- Сегмент в кавычках начинает или продолжает сегмент пути только после точки: `Kit."My Button"` - один путь, а
  `"A" "B"` (два токена без точки) - не путь; `at`/`replace` берут самый длинный префикс аргументов, который
  складывается в путь (`use` - строго все аргументы до `as`).
- Ошибки пути перечисляют кандидатов с именами в кавычках и позицией, чтобы строку можно было скопировать в правку:
  `ambiguous path Kit.a_b: candidates "a b" (f.tenn:2:5), "a_b" (f.tenn:3:5)`; `use Kit."a b"` здесь разрешает
  неоднозначность.
- `get_state` печатает путь в этой же форме: имя, для которого `NormalizeName(name) == name`, - без кавычек,
  иначе `"..."` (`scene.SegText`). Поэтому строка из `get_state` сразу годится для `at`, `read`, `select`, `gen`
  и `render`.
- Короткий путь: первый сегмент ищется вверх по дереву от места `use`; найденный узел задаёт начало пути.

### 4.3 Неоднозначность **[решено]**

Повтор имён допустим (в `docs/Example.tenn` много `item "Item"`). Ошибка `validate` только когда путь в `use`
неоднозначен; сообщение содержит позицию `use` и список кандидатов (имя в кавычках и файл:строка, 4.2), чтобы имя
можно было скопировать в путь в кавычках. Индексы `#n` не используются.
Строже вычислений: `namedItems` сейчас - плоский словарь, при повторе имени молча побеждает последний, а `"a b"` и
`"a_b"` дают одно имя **[факт]**; для `use` обе ситуации - ошибка.

### 4.4 Связи экземпляра

Связи адресуют концы по имени плюс `source-index`/`target-index`, см. 5a.9. 
**[предложение]** Связи внутри поддерева исходного узла копируются в экземпляр, связи наружу - нет. Конечные
точки копии указывают на узлы экземпляра.

### 4.5 Циклы **[решено]**

Узел, внутри которого `use` на него самого или на предка, - ошибка с цепочкой путей.

### 4.6 Экземпляр экземпляра **[решено]**

Переопределения применяются по цепочке, ближайшее (внешнее) - последним.

### 4.7 Переопределение вложенных частей **[предложение]**

Свойства в блоке `use` относятся к корню экземпляра. Вложенная часть адресуется командой `at`:

```tenn
use Kit.Dialog as d {
    title "Delete?"                  // корень экземпляра
    at Footer.Ok { title "Delete"; color red }     // путь внутри экземпляра, те же правила имён
    at Body { text "This cannot be undone" }
    replace Footer.Cancel {                          // замена поддерева целиком (аналог pen: descendants с type)
        item "Later" { title "Later" }
    }
}
```

- `at` с неоднозначным путём - ошибка `validate` (4.3).
- Сменить родителя/порядок через `at` нельзя.

**Путь `at`/`replace` [решено 2026-10-26].** Путь идёт по дереву экземпляра, как оно получилось после раскрытия
компонента: сегменты нормализуются (4.2), первый ищется среди прямых детей корня экземпляра. Сегмент выбирает:

- item или вложенный экземпляр (`use` внутри компонента, на любой глубине) по имени; следующий сегмент ищется среди
  детей его раскрытого компонента (`list.r1.Cell`: экземпляр `list`, в нём экземпляр `r1`, в нём `Cell`);
- slot по имени (безымянный - сегментом `default`); следующий сегмент ищется среди его запасного содержимого
  (`list.r1.cells.Cell`). Slot виден, пока его никто не заполнил: slot, который заполнил сам компонент во вложенном
  `use`, уже заменён своими детьми и сегментом не выбирается, а его дети адресуются как дети экземпляра.

Правила ошибок те же: несколько совпадений на любом шаге - `ambiguous path` со списком позиций (item и slot с одним
именем тоже дают неоднозначность, переименуйте один); нет такого имени - `nothing named "X" inside the instance` с
позицией команды. Путь, который кончается на slot, - ошибка: slot заполняют командой `slot <имя> { ... }` (4.7a), а не
`at`/`replace`; последний сегмент - item или экземпляр. Через `link` путь не идёт.

**Slots в `replace` [решено 2026-11-02, реализовано в go/scene].** Узлы блока `replace` подставляются вместо части
до заполнения slots блока `use`, поэтому slot, который они объявляют (`slot <имя> { … }` прямо в блоке или внутри
подставленного item), виден снаружи и заполняется как slot экземпляра:

```tenn
use Kit.Card as card {
    replace Body {
        item Box {
            slot content { item Fallback }   // запасное содержимое замены
        }
    }
    slot content { item Passed }             // попадает в slot Box, а не в Body
}
```

- `slot <имя> { … }` блока `use` заполняет slot из заменённой части; `at <путь>.<slot>.Узел` правит её запасное
  содержимое (путь через slot - как 4.7), пустой `slot {}`/`slot имя {}` очищает запасное содержимое (4.7a).
- Если slot с одним именем объявлен и в заменённой части, и у компонента, заполнение идёт в **slot замены** (её узел
  на экране; поиск заполнения предпочитает slots из `replace`). Остальные slots компонента остаются как были.
- `replace`, как и раньше, берёт узел из раскрытого экземпляра; путь до него - по 4.7, сегменты в кавычках разрешены.

Порядок со slots: все `at`/`replace` блока `use` выполняются в порядке файла, **затем** заполняются slots блока
(4.7a, 5a.7). Поэтому `at` по запасному содержимому действует, только если этот же `use` не заполняет тот slot; иначе
запасное содержимое отбрасывается вместе с правками, и `validate` даёт warning в позиции заполнения. Блок `use`
применяется после блоков вложенных `use` самого компонента (4.6): они заполнили свои slots раньше.

### 4.7a Slots как в Svelte **[решено 2026-10-25, синтаксис - предложение]**

Места в компоненте, куда экземпляр кладёт детей. Модель Svelte 4 `<slot>`: безымянный slot по умолчанию, именованные,
запасное содержимое, если экземпляр ничего не положил.

```tenn
item "Window" {                      // компонент: любой item
    auto-layout column
    item "Title" { title "Window" }
    slot "toolbar"                   // именованный, без запасного содержимого
    slot {                           // безымянный (по умолчанию), с запасным содержимым
        item "Empty" { title "Пусто" }
    }
}

use kit.Window as login {
    at Title { title "Вход" }        // переопределение части
    slot toolbar {                   // заполнение именованного slot
        use kit.Button as help { title "?" }
    }
    item "Email" { ... }             // узлы без slot - в безымянный slot, как дети без slot="..." в Svelte
    use kit.Button as ok { title "Войти" }
}
```

- В блоке `use` свойства - переопределения корня, узлы (`item`, `use`, `link`) - содержимое безымянного slot.
- Нет безымянного slot, а узлы переданы - ошибка `validate`. Имя slot, которого нет в компоненте, - тоже.
- Порядок детей в slot - порядок файла.
- **[решено 2026-10-28]** Пустой блок `slot {}` (безымянный) убирает запасное содержимое безымянного slot так же, как
  `slot toolbar {}` - именованного: заполнение есть, детей в нём нет. Без `slot {}` и без узлов запасное содержимое остаётся.
  Компонент без безымянного slot с `slot {}` в блоке - та же ошибка, что и с узлами.
- **[решено 2026-11-02]** Slots, которые объявляют узлы `replace`, - обычные slots экземпляра: `slot <имя> { … }` и
  узлы без slot (безымянный) блока `use` заполняют их, запасное содержимое адресуется `at <путь>.<slot>.…`, пустое
  заполнение убирает запасное содержимое. При совпадении имён приоритет у slot из `replace` (4.7).
- Генерация: Svelte 4 - `<slot>` / `<slot name>` / `slot="..."` (snippets не используются); Svelte 5 - snippets (`{@render children()}`); React - `children` и именованные props;
  gowt - дети контейнера.
- Параметры slot (как `let:` в Svelte 4) - не в v1.
- **[решено 2026-10-26]** Slots вложенных `use` остаются открытыми, пока не закончен внешний `use`, и адресуются из него
  путём (4.7): `at list.r1 { slot cells { ... } }` заполняет slot `cells` экземпляра `r1`, а `at list.r1.cells.Cell { ... }`
  правит его запасное содержимое. Узлы без `slot` и `slot <имя>` блока `use` по-прежнему относятся только к slots самого
  компонента: slots вложенных экземпляров безымянным заполнением и поиском по имени не задеваются.

Отдельной команды `frame` нет **[решено 2026-10-25]**: любой item может иметь детей и auto-layout.
Окно, карточка, диалог - компоненты библиотеки из таких item, на экранах их берут через `use` со slots.

### 4.8 Detach **[предложение]**

Операция редактора/MCP `detach(path)`, не синтаксис: `use` заменяется копией поддерева (с применёнными
переопределениями) как обычными узлами. Обратно не превращается.

### 4.9 Переименование **[решено]**

Переименование узла ломает `use` по пути; нужно переименование по всему workspace (этап 3) и в MCP.

## 5. Item с детьми и auto-layout

Имя `layout` занято (раскладка диаграммы element: `left`/`right`/`middle` для текста item и алгоритмы element),
для auto-layout не используется.

```tenn
item "Card" {
    auto-layout column
    gap 8
    padding 16 12
    align center
    justify space-between
    width 320
    height hug
    min-height 100
    corner-radius 8
    clip yes
    item "Title" { title "Order #${demo.orders.first.id}" }
    item "Row" {
        auto-layout row
        width fill
        wrap yes
        line-gap 4
        item "Chip" { width 60 }
        item "Badge" { absolute yes; pos 4 4 }

}
```

проценты, `fill` с запасным значением (`fit_content(100)` в pen), выравнивание строк при `wrap`, `space-around`.

Ограничения `gfx`/`gfx/layout`, найденные реализацией в `go/scene` (**[факт]**):
- `layout.Node.Pad` у листа (без детей) не действует: поля вокруг текста листа `go/scene` вшивает в `LeafW`/`LeafH`;
- корень `auto-layout abs` с hug считает размер по максимуму `X+W`, отрицательные позиции в `RW`/`RH` не попадают (в границы сцены попадают);
- SVG-писатель gowt пишет у текста только `font-family` из `Font.Name`: у item с `font-family`, весом, курсивом или интервалом в SVG шрифт не тот (PNG через `gfx/offscreen` верный).

Существующие `width`/`height` у item brain map - числа (раздел docs.md "Boundaries"); слова `hug`/`fill` - только у узлов
внутри item с `auto-layout` **[предложение]**. Вне такого item слово вместо числа - ошибка `validate`. Значения `width` как выражение
`${...}` разрешены и сейчас; для `hug`/`fill` выражение не подставляется.

## 5b. Стили компонента (варианты) [предложение 2026-11-01]

Один компонент описывает все варианты; варианты не копируются в отдельные элементы, как сейчас в
`dev/design/tenn/lib/actions.tenn` (`Button/primary/large`, `Button/primary/medium`, ...).

Имена и место те же, что уже работают для item в классических диаграммах (`styles { имя { ... } }` на
элементе, `use-style имя` у item, `render/scene.go`): сцена берёт тот же синтаксис, иначе два похожих
механизма в одном формате.

```tenn
element "Button" {
    styles {
        primary   { color #6b3ad3; text-color #ffffff }
        secondary { color #ffffff; border-color #1725471a; text-color #172547 }
        ghost     { color #00000000; text-color #6b3ad3 }
        large     { height 48; padding 0 16 }
        medium    { height 40; padding 0 12 }
        outlined  { border-color #1725471a }
        kind      one-of primary secondary ghost
        size      one-of large medium
        extras    any-of outlined
    }
    item Btn {
        auto-layout row; gap 8; align center; justify center; corner-radius 8
        use-style primary medium
        item Label { title Button; font-size 14; font-weight 500 }
    }
}
```

Место вставки выбирает вариант; остальное - умолчания компонента:

```tenn
use Actions.Button as save { at Btn { use-style secondary large } at Btn.Label { title Save } }
```

Правила ([движок готов 2026-11-01], `go/scene/styles.go`):

- `styles { имя { команды } }` - именованный набор свойств в области элемента; узел выбирает его
  командой `use-style имя`, можно несколько, для каждого свойства побеждает последний по порядку;
- объявленные для компонента группы: `имя one-of a b c` (ровно один) и `имя any-of a b` (любое
  число). Инспектор показывает группу `one-of` переключателем, `any-of` - чекбоксами; список валидных
  стилей компонента - это его группы. Строка без `one-of`/`any-of` группой не считается и пропускается
  (ошибки нет); [реализовано 2026-11-01]: `scene.Node.StyleGroups`, `scene.StyleScope`, `scene.StyleRefs`,
  секция Styles в `go/app/inspector_scene.go` - переключатель выбирает стиль на место прежнего, снять
  выбор `one-of` кликом нельзя (только `use-style -имя`), чекбокс `any-of` дописывает стиль в конец;
- **стиль встаёт туда, где написано `use-style`** (решение владельца 2026-11-01): свойства выше него -
  умолчания, стиль их перекрывает; свойства ниже - перекрывают стиль; `at` с места вставки пишется в конец
  и главнее всего. Так автор компонента сам решает, что важнее:
  ```tenn
  item Btn { auto-layout row; gap 8; height 40; use-style large; }   // размер даёт стиль
  item Btn { auto-layout row; gap 8; use-style large; height 40; }   // размер 40 всегда
  ```
- на месте вставки `use-style` добавляет стиль к умолчаниям компонента; убрать умолчание - `use-style -имя`;
- вложенный блок `Label { ... }` внутри стиля задаёт свойства ребёнка с этим именем (селектор потомка,
  как в CSS), глубже - так же вложенно; эти свойства - умолчания ребёнка, его собственные и его стиля главнее;
- **цвет текста и шрифт наследуются вниз** (решение владельца 2026-11-01): `text-color` и `font-family`,
  `font-size`, `font-weight`, `font-style`, `letter-spacing` берутся у ближайшего предка, который их задал;
  цвет текста по умолчанию - контраст к своей видимой заливке, а без заливки - унаследованный; иконка без
  `color`/`border-color` заливается унаследованным цветом текста. Заливка (`color`), рамка, размеры, тень,
  `opacity`, раскладка не наследуются - поэтому `primary { text-color #ffffff }` на коробке красит всё её
  содержимое, а `Label { ... }` в стиле нужен только для отличий;
- **`none` и `transparent`** - цвет без заливки (владелец 2026-11-01): `border-color none`, `color none`,
  `shadow 0 0 0 none`; это то же, что альфа 0 рисует и так, но читается как намерение;
- темы (этап 1e.6) строятся тем же механизмом: `dark { ... }` в `styles` и `use-style dark` на корне.

Движок: один проход после развёртывания (`go/scene`): собрать `styles` области, вставить свойства стиля
в точку `use-style`, вложенные селекторы разложить по детям, группы отдать инспектору (`go/app`).
**[реализовано]**, `afterUseStyle` и `inheritProps` в `go/scene/styles.go`.

Проверено на прототипе `examples/button-styles.tenn`: один `Button` (14 стилей, 4 группы) покрывает 48
вариантов каталога дизайн-библиотеки (по шесть видов, четыре размера, с иконкой и без). Чего не хватает для библиотеки: нет
`aspect-ratio` (у icon-only ширина дублирует высоту в стиле размера); `use-style` в блоке самого `use`
игнорируется - это закрывает 5c; нейтральный член `one-of` приходится объявлять пустым стилем.

## 5c. Компонент и его параметры [реализовано 2026-11-01]

Сейчас компонент - это обычный `element`, а его настройка на месте вставки - `at <путь> { свойства }`.
Хочется, как в Svelte: элемент объявлен компонентом, у него есть объявленные параметры с умолчаниями, и
место вставки задаёт их по имени, не зная внутренних путей.

```tenn
element "Button" {
    kind Component
    export let title = "Button"
    export let kind = primary
    export let size = medium

    styles {
        primary   { color #6b3ad3; text-color #ffffff }
        secondary { color #ffffff; border-color #1725471a; text-color #172547 }
        large     { height 48; padding 0 16 }
        medium    { height 40; padding 0 12 }
        kind      one-of primary secondary
        size      one-of large medium
    }

    item Btn {
        auto-layout row; gap 8; align center; justify center; corner-radius 8
        use-style ${kind} ${size}
        item Label { title ${title}; font-size 14; font-weight 500 }
    }
}

use Actions.Button as save { title "Save"; kind secondary; size large }
```

Правила ([реализовано в `go/scene`, `go/app` ждёт]):

- `kind Component` - команда **внутри блока элемента** (и `kind Library`/`Application` в корне файла):
  признак компонента, он попадает в picker компонентов, а не в список экранов. В шапке (`element "X" kind
  Component`) писать нельзя: классический слой читает содержимое элемента в позиции 2 (`element "X" { ... }`),
  лишний аргумент сдвигает блок, и приложение, рисующее классику, не видит у элемента ничего. Такой `kind`
  даёт предупреждение и не применяется. Файлы и элементы без признака - экраны; отдельно `kind Screen`.
- `export let <имя> = <значение>` объявляет параметр с умолчанием; без `=` параметр обязателен. Работает и в
  `item`, и в `element`: компонентом может быть один узел (`item Chip { export let label = …; styles { … } }`),
  его вставляют `use Kit.Chip as a { label "One" }`, а открытый сам по себе узел показывает умолчания. `styles`
  в `item` тоже читаются, и стиль корня экземпляра ищется в определении, а не в месте вставки.
  Значение - одно слово или список слов (`export let extras = outlined`); на месте вставки список пишется
  так же (`extras outlined rounded`), а `use-style ${extras}` называет все стили списка - так задаётся
  группа `any-of`.
- в сцене `${...}` **вычисляются тем же движком**, что и в классике (`go/exec` на goja): параметры
  `export let` попадают в область видимости экземпляра как обычные переменные, поэтому `title ${title}`
  и `width ${size + 12}` работают. Движок сцены получает вычислитель через `scene.Options.Eval` и сам от
  goja не зависит (`tenn-render` может передать `NoEvaluate`).
- параметр, значение которого входит в группу `one-of` из `styles` (5b), инспектор показывает
  переключателем; `any-of` - чекбоксами; остальные - полем.
- место вставки задаёт параметры по имени без пути: `use ... { title "Save"; kind secondary }`; старые
  `at`/`replace` остаются для нестандартных правок.
- те же `export let` служат шаблонам (1d.5): шаблон компонента - текст с `${имя}` и `<slot>`, генератор
  подставляет параметры и детей, так из компонента получается код.

Решено владельцем (2026-11-01): выражения в сценах вычисляются, а не подставляются текстом; `kind` есть и
у элемента, и у файла.

Как сделано (`go/scene/params.go`, `go/scene/load.go`):

- `scene.Node.Type` - `kind` в нижнем регистре (`""` - экран), `Node.Params` и `Node.Param(name)` - параметры;
  неизвестный `kind` - предупреждение, `export let` вне элемента - свойство, дубликат - предупреждение;
- значение с места вставки вычисляется в области **вызывающего** (`use Inner { n ${n + 1} }` видит параметры
  внешнего компонента), умолчание - в области определения; тело экземпляра видит только свои параметры,
  элемент без параметров наследует область, в которой написан;
- вычисление всех свойств экрана идёт **до** `applyStyles`, поэтому `use-style ${kind} ${size}` выбирает
  стиль; меняются только копии `RNode` (`Prop.Val`), исходные `Prop` общие и не трогаются;
- необъявленное имя в блоке `use` остаётся свойством корня экземпляра; обязательный параметр без значения -
  ошибка сборки и `check`.

Корень экземпляра (`use`), у которого есть содержимое, - контейнер: своей коробки не рисует (белая заливка
закрыла бы экран), а его имя - псевдоним, а не текст. Одиночный элемент-компонент без детей рисуется как
обычный item.

Инспектор параметров (переключатель для `one-of`, чекбоксы для `any-of`, поле для остальных) ещё не сделан.

### Шаблоны: код из компонента (1d.5) [реализовано 2026-11-02, ждёт подтверждения]

Компонент отдаёт **текст кода** (Svelte, React, gowt - что написано): блок `template` в его теле. `template` -
обычная команда с новым смыслом только внутри блока элемента, файлы без неё читаются как раньше; в item и в
корне файла `template` остаётся пользовательским свойством.

```tenn
element "Button" {
    kind Component
    export let title = "Button"
    export let tone = secondary
    template %{
<button class="btn-${tone}">${title}<slot/></button>
    }
    item Btn {
        auto-layout row
        item Label { title ${title} }
        slot
    }
}
```

- **Форма записи.** `template %{ ... }` - markdown-литерал (`%{`/`}` уже есть в лексере): содержимое не
  разбирается как команды, поэтому это рекомендуемая форма для настоящего кода. `template { ... }` - блок: текст
  берётся из файла дословно (байты между `{` и `}`), но лексер читает его командами - каждая строка должна
  начинаться со слова, а `{`/`}` внутри считаются блоками (две пары скобок в одной строке дают warning «2 blocks
  in one command»). `template "<одна строка>"` читается как текст строки. В `%{ ... }` скобки должны быть
  сбалансированы: лексер считает их вложенность. Ничего в грамматике не менялось (раздел 1).
- **Отступ снимается** (`dedent`): пустые строки по краям и общий отступ строк убираются, поэтому код шаблона
  пишется на уровне компонента, а печатается с колонки 0.
- **`${имя}`** - параметр компонента (5c) и любое выражение: вычисляется тем же `Options.EvalVars`, что и сцена
  (раздел 6), поэтому список слов (`extras outlined rounded`) и `width ${size + 12}` работают. Значение берётся из
  `values` (`-set`), иначе из блока `use`, иначе умолчание объявления.
- **`<slot/>`** - содержимое блока `use`: узлы без `slot <имя>` (безымянный слот). **`<slot имя/>`** - узлы
  `slot <имя> { ... }` того же блока. Узел подставляется своим `title` (выражения вычисляются), а без него - именем.
  Другие формы (`<slot></slot>`, `<slot name="x"/>`) остаются текстом - так генерируется настоящий слот Svelte.
  Порядок - порядок файла. Чтобы блок `use` вообще принял узлы, у компонента должен быть сценовый `slot` в теле
  (4.7a): шаблон его не заменяет, он только читает тот же блок.
- **API `go/scene`:** `Node.Template` (`Template{Text, Pos}`) и
  `(*scene.Tree).Render(node *Node, values map[string]string, o Options) (string, error)`. `node` - элемент-компонент
  или `use` его (тогда значения и слоты берутся из блока этого `use`). Ошибки возвращаются вместе с текстом как
  `scene.Errors` с позицией; диагностику дерева `Render` не меняет, поэтому вызывать его можно сколько угодно раз.
- **CLI:** `tenniarb gen [-root DIR] [-set имя=значение]... FILE ELEMENT` печатает текст в stdout и добавляет
  перевод строки, если его нет. Коды как у `check`: 0 - напечатано, 1 - ошибки файла или шаблона, 2 -
  использование или файл не читается. `ELEMENT` - путь имён от корня файла: элемент (`Button`) или экземпляр
  (`Screen.col.save`), путь разрешается теми же правилами, что `use` (4.2).

Ошибки (error, а не warning): неизвестный параметр в `-set` (со списком параметров); обязательный параметр без
значения; `<slot/>` без содержимого (в том числе у элемента, отрендеренного без `use`); `${...}` без вычислителя или
с упавшим выражением. Второй `template` в элементе - warning, берётся первый.

Не сделано: генерация нескольких файлов и форматов за один прогон, знание Svelte/React/gowt - формат задаёт сам
текст шаблона; запасное содержимое `<slot>запас</slot>`; параметры слотов (как `let:` в Svelte 4); вложенный
компонент в слоте подставляется именем, а не своим шаблоном; значения блока `use` не видят параметров внешнего
экземпляра; `tenn.Compact` шаблон не сохраняет - текст шаблона живёт в байтах файла (`Node.Range`), а не в
дереве команд, поэтому печатать файл с шаблонами принтером нельзя.

      сплошная заливка, `color` без слова `linear` не меняется. Меньше двух цветов, не число в угле, не цвет, позиции не у всех
      или вне порядка - warning и заливка по умолчанию. Цвет текста по умолчанию считается от первого видимого цвета
      градиента. Градиент относится к заливке бокса: у иконки (`path`), `border-color` и `text-color` градиента нет (warning).
      С `shadow` градиент рисуется поверх непрозрачной подложки цвета первого стопа (в `gfx` нет градиента с тенью), поэтому
      прозрачные стопы покажут подложку. `penimport` пишет линейный градиент pen целиком: `rotation` (градусы против часовой
      от "вверх") переводится в `360 - rotation`; градиент с `center`, длиной не 1 или не линейный остаётся первым цветом
      (`gradient fill (first stop)` в отчёте). Соответствие направления pen проверено только по схеме (`0° up, 90° left`), не по
      картинке Pen.app.
    - **[реализовано в go/scene, ждёт подтверждения]** `corner-radius TL TR BR BL` (порядок CSS) рисуется через

## 6. Выражения `${...}`

**[реализовано 2026-11-01, `go/scene`]** В сцене `$()` и `${...}` вычисляются: `scene.Options.Eval`
получает код выражения (без `$()`/`${}`), а для строки с `${...}` - шаблон в обратных кавычках, и возвращает
значение текстом; реализация - `exec.SceneEval` на goja, без области item. Выражение можно писать вместо значения
любого свойства: `width ${20 * 4}`, `color ${brand}`, `title "Hi ${who}"`. Без `Options.Eval` выражение -
предупреждение, свойство считается незаданным; упавшее выражение - тоже предупреждение, значение пустое. Ошибка
не роняет сборку. Кэш - на одну сборку, по свойству узла (свойства сцены общие между экземплярами, поэтому
вычисляется копия). `Load`/`validate` ("`tenniarb check`") раскладку делает без вычислителя и про выражения
молчит: значение там неизвестно, а не сломано; предупреждение остаётся у `Build` без `Options.Eval`.

Сейчас **[факт]** (`execution.ts`): выражение вычисляется в контексте одного element (`ElementContext`);
`items.<Имя>` (через `convertNameJS`) - item того же element; `parent.items`/`parent.links`; `inputs`, `outputs`,
`edges` - связанные item; `byTag(tag)`, `sum(tag, field)`; приложение вычисляет только показанный element
(`setElement`); пересчёт - до 100 итераций, затем останов без ошибки (TODO в коде).

**[решено]** `${...}` получает те же пути, что `use`:

```tenn
element "Login" {
    element "demo" --from-file "../data/demo.tenn"
    item "Screen" {
        item "Greeting" { title "Hi, ${demo.users.Alice.name}" }
        item "Count" { title "${sum('price') + demo.fee}" }   // старые функции работают как раньше
    }
}
```

Требования **[решено]**:
- вычислять и element, на который ссылаются, без показа;
- зависимости между element-ами: правка демо-данных пересчитывает все экраны, которые на них ссылаются;
- цикл между element-ами - ошибка с путём цикла, а не зависание (замена лимита 100 итераций для межэлементных ссылок);
- `${...}` из смонтированного файла исполняет его JS - для библиотек вне своего workspace нужен флаг доверия.

**[предложение]**:
- Первый сегмент пути в `${}` ищется вверх по дереву, как в `use` (раздел 4.2). Порядок разрешения имени:
  локальные имена item/свойств текущего узла, затем `items`, затем пути. Коллизия имени свойства и алиаса - ошибка
  `validate` (см. вопрос 6).
- Смонтированный файл считается в собственном контексте, а не в контексте места монтирования (иначе один файл даёт
  разные значения в разных местах) - **[предложение]** roadmap.
- Привязка: выражение в разметке сцены = привязка с пересчётом по графу зависимостей (уровень item/свойство;
  в коде есть `ItemContext.dependencies`), а не по всему element, как в `ExecutionModel`.
- Флаг доверия **не пишется в `.tenn`** (файл не может сам себя доверять); хранится в настройках workspace/пользователя.
  Файлы внутри корня workspace доверенные по умолчанию.
- Значения демо-данных в экземпляре `use`: выражения в переопределениях считаются в контексте места `use`,
  выражения внутри определения - в контексте файла определения.

## 9. Совместимость

**Строки после `//` считаются верно. [факт, исправлено 2026-11-02]** Все порты лексера (Swift `TennLexer`/`SlowLexer`,
`web/packages/core`, `go/tenn`) вели счёт после `//`-комментария дважды: цикл комментария увеличивал номер строки и
оставлял перевод строки главному циклу, тот считал его ещё раз. Диагностика сдвигалась вниз на число комментариев
выше. Теперь комментарий останавливается на переводе строки, не потребляя его, и строку считает только
`processNewLine`; голдены `web/fixtures/*.parse.json` перегенерированы от Swift-парсера.

**Два блока в одной строке - одна команда. [факт, проверено 2026-11-01]** `item a { item b { … } item c { … } }` и
`use B as x { at A { … } at C { … } }` без переводов строк читаются как одна команда со склеенными блоками: имена
второго (`item c`, `at C`) пропадают. Блок не заканчивает команду - её конец только перевод строки или `;`
(голдены `go/tenn` и web это фиксируют, поведение общее со Swift-парсером). `go/scene` предупреждает о таком
склеивании (`joinedBlocks`), поэтому `tenniarb check` показывает его как warning. **Один блок - одна строка**;
это правило для любого генератора `.tenn`.

  (совпадение `template"` в `AntiCRM.tenn` - имя item с переводом строки внутри кавычек, а не команда). Смысл действует
  только в блоке элемента; в item и в корне файла `template` остаётся прежним пользовательским свойством.
- `validate` предупреждает, если старое пользовательское свойство совпадает по имени с новым и стоит там, где новое действует.

### 9.5 Канонический компактный вид **[решено 2026-10-26]**

`tenn.Compact` (`go/tenn/compact.go`) для файлов, которые читают агенты (вывод `penimport`). `tenn.ToStr` не меняется:
это байт-в-байт печать Swift.
- Отступ 2 пробела на уровень, команды разделены переводом строки.
- Блок, где только команды без вложенных блоков и без переводов строки внутри, печатается в одну строку:
  `item "A" { title x; color red }`. Пустой блок - `{}`. Строка с отступом не длиннее 160 байт, иначе блок раскрывается.
- Строка без пробелов и спецсимволов (буквы, цифры, `_ - . #`), не похожая на число, печатается без кавычек. Остальное
  (пробелы, пустая строка, `"2024"`, `{ } ; / % @ $ ' "`) - в кавычках. Бескавычечное слово читается как `Ident`, а не
  `StringLit`; `GetIdentText` и go/scene различают их только для чисел, поэтому числоподобные строки остаются в кавычках.
- `;` и перевод строки - равноправные разделители команд и в Go, и в Swift (`TennLexer`: `;` и `\n` дают `semiColon`).
  Перевод строки перед строкой или `{` продолжает команду, поэтому `{` всегда на одной строке с командой.
- Порог 160 выбран по измерению на трёх импортированных файлах (o200k_base, прокси, не токены Claude): 60 / 100 / 160 /
  без предела дают 213k / 209k / 199k / 197k токенов для самого большого файла; от 160 выигрыш меньше 1%, а строки
  остаются читаемыми. Пропуск кавычек даёт ещё около 3% токенов.

### 9.6 Вид вывода `penimport` **[решено 2026-10-28]**

`penimport` печатает `tenn.CompactAs` с отступом в табуляцию и с упаковкой (`tenn.CompactStyle`): в раскрытом блоке
подряд идущие команды без блока делят строку через `; ` до порога 160.
- Не пишется то, что go/scene и так предполагает: `display` у item (читается только у `link`), `color #00000000` и
  `line-width` без `border-color` внутри раскладки, `line-width 1`, `text-color #000000` без `color`, `auto-layout row`
  у листа в раскладке без свойств контейнера. Переопределение в `use`/`at`, повторяющее значение компонента, тоже
  пропускается, кроме значений-переменных (тема экземпляра может быть другой) и узлов внутри вложенного экземпляра.
- Раскладки переносятся как в `.pen`: повторы не ищутся, компоненты из них не выделяются (отдельная функция редактора).

## 10. Сравнение с pen.dev (`.pen`)

| Понятие | `.pen` (схема 2.21) | `.tenn` (этот черновик) |
|---|---|---|
| Формат | JSON, шифруется (доступ только через MCP) | текст, git-diff, merge |
| Дерево | `children` массивом, вложенность = frame | два уровня: `element` и содержимое, вложенность = item с детьми |
| Контейнер | `frame`, `group` | `item` с детьми; `group` - нет |
| Раскладка | `layout: none/vertical/horizontal` | `auto-layout abs/column/row` |
| Gap, padding | `gap`, `padding` (1/2/4 значения) | `gap`, `padding` (1/2/4) |
| Главная ось | `justifyContent` start/center/end/space_between/space_around | `justify` без `space-around` |
| Поперечная ось | `alignItems` | `align` |
| Размеры | `fit_content`, `fill_container`, `fit_content(100)` | `hug`, `fill`; без fallback |
| min/max | нет | `min-*`, `max-*` |
| Перенос | нет | `wrap`, `line-gap` |
| Абсолютное положение | `layoutPosition: absolute` | `absolute yes` + `pos` |
| Клип | `clip` | `clip` |
| Компонент | `reusable: true` на узле | любой узел, пометки не нужно **[решено]** |
| Экземпляр | `ref` по `id` | `use <путь по именам> as <имя>` |
| Переопределения | `descendants` по пути `id`; наличие `type` = замена | блок `use`, `at <путь>`, `replace` **[предложение]** |
| Slot | `slot: [id...]` | `slot yes` **[предложение]** |
| Идентичность | `id` (уникален, без `/`) | имя; повтор допустим, неоднозначный путь = ошибка |
| Переменные, темы | `variables`, `themes`, `$name` | нет; выражения `${...}` и стили `styles` |
| Монтирование файла | `imports`: алиас файла, плоский, на весь файл | `element ... --from-file`, на узел дерева, область видимости, подмена **[решено]** |
| Вычисления | нет | `${...}` (JS) с путями между element-ами |
| Связи узлов | нет | `link` |
| Скрипты, шейдеры, browser, prompt | есть | нет, не цель **[решено]** |
| Нативные виджеты | нет | `native gowt.X` **[предложение]** |
| Комментарии на узлах | узлы `note`/`prompt`/`context` в сцене | `comment` в файле **[предложение]** |

## 11. Открытые вопросы

1. Синтаксис вложенных переопределений (`at`/`replace`/`slot`) и сегменты с пробелами: имена только идентификаторы
   или путь строкой (`use "my.lib/Primary button"`).
2. **[закрыт, 5a.3]** Регистр: в примере roadmap `my.lib.components.button` - путь строчными, а имя узла, вероятно, `Button`.
   `convertNameJS` регистр не меняет. Чувствителен ли путь к регистру?
3. **[снят]** Семантика `as` у `import` с точками: `import` из формата убран (раздел 3).
4. **[закрыт, 5a.5]** Область видимости `--from-file` в корне файла: весь файл или только дальше по тексту.
5. **[частично закрыт, 5a.9]** Копирование связей экземпляра (4.4) и конечные точки `link`: строки-имена в пределах element сейчас
   (`source-index` для повторов) - как адресовать вложенные item (путь с точками?).
6. Первый сегмент пути в `${}` против локальных имён и свойств (`width`, `pos`, `utils`, `items`, `parent` уже в scope).
7. Несколько целей `native` и источник схемы фасада gowt (формат `apidump` не исследован).
8. Порядок узлов при записи: старая модель переставляет (9.1). Для детей item порядок сохраняется. Нужен ли
   гарантированный порядок на уровне element (z-order)?
9. Имена из цифр: сегмент `1` или `2.5` лексится как число, путь `a.1` - symbol, но `1.2` - `floatLit`.
10. Комментарии `//` теряются при сохранении; комментарии на узлах требуют либо команды `comment`, либо
    сохраняющего комментарии лексера.
11. Правка внутри смонтированного поддерева (запись в чужой файл) и доверие `${...}` из импорта: где хранить флаг.
12. Не выражается в `layout`: `align` на ребёнке, проценты, fill с запасным значением, `space-around`, выравнивание
    строк при `wrap` - ограничение движка принимаем или расширяем gowt.

## 13. Анимации [реализовано в `go/scene` 2026-11-02, ждёт подтверждения]

Запрос владельца: на кнопку можно поставить «крутилку», а изменения в макете выглядят живыми.

```tenn
element "Button" {
    animation spin {
        from { rotate 0 }
        to { rotate 360 }
    }
    animation fade {
        0%   { opacity 1 }
        100% { opacity 0.4 }
    }
    styles {
        idle    { }
        loading { animation spin 1s linear infinite; Icon { path "M2 8a6 6 0 1 0 6 6" } }
    }
    item Btn {
        animation fade 200ms ease-out
        transition color 150ms ease-in-out
    }
}
```

Правила ([факт] по `go/scene/anim.go`, `go/scene/svg.go`):

- `animation <имя> <длительность> [easing] [repeat]` - команда узла или строка стиля: играет кадры блока с
  этим именем. Длительность `300ms`, `1s`, `1.5s`; easing `linear`, `ease`, `ease-in`, `ease-out`,
  `ease-in-out` (по умолчанию `ease`, как в CSS); repeat - число (`2` - два прохода) или `infinite`.
- блок кадров `animation <имя> { <кадр> { свойства } ... }` пишется на узле или выше него (элемент, item,
  файл): узел видит свои блоки и блоки предков, ближний перекрывает внешний. Кадр - `from`, `to` или
  процент `0%..100%`; кадры сортируются по смещению, первый - то, что рисует статичная картинка.
- одно имя на много узлов: блок один, у каждого узла свои длительность, easing и repeat.
- анимируются только `rotate`, `scale`, `opacity`, `color`, `border-color`, `text-color`, `pos`. Раскладка
  (`width`, `height`, `gap`, `line-gap`, `padding`, `min-width`/`max-width`/`min-height`/`max-height`,
  `auto-layout`, `wrap`, `align`, `justify`, `absolute`) не анимируется: предупреждение, кадр
  игнорируется. Любое другое свойство в кадре - такое же предупреждение.
- `transition <свойства> <длительность> [easing]` (`transition color 150ms ease-in-out`, свойства через
  пробел или запятую) разбирается и проверяется; рендера перехода нет (ниже).
- время (`300ms`) и `%` в кадрах - новые виды значений формата; `%` в `width` остаётся предупреждением
  (размер становится `hug`, 5a).

Рендер ([факт] по `go/scene`):

- сборка: первый по смещению кадр пишется в узел обычными свойствами, поэтому PNG и статичный SVG
  показывают первый кадр (`opacity`, цвета, `pos`). `rotate` и `scale` в статичную картинку не попадают -
  узел стоит так, как написан; для «крутилки» `from { rotate 0 }` и есть первый кадр.
- SVG: `Screen.WriteSVG` пишет документ через `gfx.WriteSubtreeSVGWith` и добавляет `<style>` с
  `@keyframes <имя>` и `animation: <имя> <длительность> <easing> [repeat]` в `style` группы узла.
  `rotate`, `scale`, `pos` - индивидуальные CSS-свойства (`rotate`, `scale`, `translate`), они добавляются
  к `transform` группы и не сдвигают узел; `opacity` - `opacity`, `color` и `text-color` - `fill`,
  `border-color` - `stroke`.
- заливка и цвет текста в кадре - одно CSS-свойство `fill`: у узла, где есть и текст, и заливка, кадр
  меняет оба.
- `pos` в кадре виден только у `absolute` узла: в раскладке место задаёт layout, а не `pos`.

Чего нет:

- `gfx` не даёт ни CSS, ни id узла в SVG (`gfx.SVGOptions` знает только фон), поэтому `Screen.WriteSVG`
  вставляет стиль по порядку групп `<g transform="matrix(...)">`. Для gowt нужен хук: id или класс у узла,
  либо строка CSS в `SVGOptions`; тогда сопоставление по порядку уйдёт (см. комментарий в `scene/svg.go`).
- переходы (`transition`) не рендерятся: у сцены нет состояния «стиль сменился, играй переход», смена
  стиля - это пересборка. Нужен переход между двумя сборками или аниматор в приложении.
- аниматора узлов сцены нет ни в `gfx` (`gfx/anim.go` - спрайты), ни в приложении; macOS-версии нужен
  Core Animation. Формат для всех трёх общий.
- связь с вычислениями не определена: `${...}` пересчитываются при сборке, кадры идут по часам.
- `animation` в библиотеке компонентов как часть стиля варианта (`loading`) работает (стиль - обычные
  свойства), но состояние «какой вариант сейчас» в формат не входит.
